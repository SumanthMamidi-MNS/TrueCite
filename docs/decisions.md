# Decisions log

- 2026-09-12: Use `pypdf` for PDF parsing in Phase 1 instead of `unstructured`, because `unstructured`'s system dependencies (poppler/tesseract) are heavy to set up on Windows and pypdf is sufficient for text-based legal PDFs; revisit if scanned/image-only PDFs show up in the corpus.
- 2026-09-12: Local git repo initialized, no GitHub remote yet — commits stay local until the user explicitly asks to push/create a repo.
- 2026-09-12: Python dependency management via venv + requirements.txt (user preference).
- 2026-09-12: Structural chunker uses a cascading strategy (numbered sections/paragraphs -> subsection split if oversized -> paragraph fallback if no numbering detected) instead of one fixed pattern, because the corpus's three document types (Act, numbered-paragraph guideline, plain FAQ) each use different structure.
- 2026-09-12: Section-number detection runs once globally over a document's full body text (not per-chapter), because Act section numbers are continuous across chapters — per-chapter matching let page-footnote numbering (which restarts low) collide with real section numbers again at each new chapter.
- 2026-09-12: Square-bracket amendment-insertion markers (e.g. "3[11A. ...") are stripped from page text before chunking — they're pure editorial typography in Indian bare acts, and left in place they hide the real section number from line-start detection (was silently merging section 11A's text into section 11).
- 2026-09-12 (superseded, see below): Lettered definition clauses were initially left un-split.
- 2026-09-12: `chunk_document`'s `body_start_anchor` now raises if the anchor string isn't found, instead of silently chunking the whole document (TOC included) as body text. Caught a real bug this way (PDF extraction's stray spaces/line-wraps broke both new anchors) instead of shipping bad output that looked plausible.
- 2026-09-12: Oversized sections with no numeric "(1)"/"(2)" subsections (AYUSH-2025's decimal "3.1" headings, WIPO toolkit's named headings) now fall back to paragraph-grouping rather than a second dedicated parser for decimal/named headings — reuses the same fallback machinery as unstructured documents instead of adding a new strategy, at the cost of citing by paragraph position instead of a specific numbered subsection for these two docs.
- 2026-09-12: Paragraph splitting/merging reworked to operate on character spans (start,end) instead of extracted strings re-searched in the original text — the string-search approach crashed on real input because reconstructed "\n\n"-joined text didn't always match the source's original whitespace verbatim.
- 2026-09-12: Vector store for Phase 2 is ChromaDB (embedded library, matches PRD §7), not Qdrant, even though Qdrant is already running in the user's Docker Desktop. Reason: at this corpus size (288 chunks) performance is a non-issue either way, and ChromaDB has no separate server to start/forget-to-start, which removes friction during active retrieval-logic iteration. Qdrant's real advantages (native hybrid search, richer filtering, built for concurrent scale) matter for production multi-user deployment, which the PRD's non-goals explicitly rule out for this project.
- 2026-09-12: Lettered clauses ("(a)", "(b)", ... "(p)") are now split into their own chunks whenever a section enumerates >=3 of them and has no numeric subsections of its own — regardless of total section length. Motivated by a concrete finding while hand-checking Phase 2's gate queries: Section 3 (16 unrelated statutory exclusions in one chunk) didn't surface for a plain-language TK-patentability question even in the top 20 vector results, because pooling all 16 clauses' embeddings diluted clause (p)'s specific signal (isolating it alone raised cosine similarity 0.455 -> 0.568). Each clause chunk keeps the section's intro text prepended so it isn't read out of context.
- 2026-09-12: Lettered-clause matches are filtered to a strictly-increasing sequence (same defense as the existing section-number monotonic filter), because a lettered marker is short enough that a mid-sentence cross-reference (e.g. "...described in clause (b) of this section...") can start its own PDF-wrapped line and be mistaken for a second, spurious "(b)".
- 2026-09-12: Fixed a second, independently-discovered instance of the "content silently dropped before the first regex match" bug class: `_split_section_body`'s numeric-subsection splitting was dropping subsection "(1)"'s entire text whenever it appeared inline with the section heading (the normal case: "19. Powers...—(1) If...") rather than on its own line. Also had to loosen the function's "need >=2 matches to bother splitting" gate to count this inline "(1)" toward the total, since a section with exactly two subsections ("(1)" inline + "(2)" on its own line) was hitting the gate before ever reaching the fix.
- 2026-09-12: Added a pytest suite (tests/, 22 tests) covering chunking, BM25, RRF fusion, and authority metadata — formalizes what had been ad-hoc verification via inline scripts into a real regression suite that would catch these bugs automatically going forward.
- 2026-09-12: After the clause-splitting fix, Section 3(p) still doesn't rank in the top 20-30 vector results (or BM25, or hybrid) for "Can traditional knowledge be patented in India?" — verified this is a vocabulary/framing gap (the statute never uses the word "patent"; the query does), not a remaining chunking defect, and did not chase it further with more chunking engineering since that would be fixing the wrong layer. Accepted as a known challenge to carry into Phase 5 (Layer 3 should be able to promote an Act-level citation over a same-topic Guideline citation, since similarity ranking alone won't reliably surface terse statutory clauses for natural-language questions) rather than something Phase 2/3 chunking or retrieval tuning can fully solve.
- 2026-09-12: Layer 1 confidence-gate threshold set at 0.90 (ChromaDB L2-on-normalized-embeddings distance), calibrated against real (query, distance) evidence rather than guessed: every genuinely on-topic query tested had best-hit distance <= ~0.63; every genuinely unrelated query (cricket rules, a cake recipe, boiling point, LLC tax) scored >= ~0.99. A real middle zone exists (0.76-0.82) for queries the corpus is topically related to but doesn't actually answer with specifics (e.g. asking for a fee *amount* when the Act only says fees are "as may be prescribed") — the threshold deliberately lets these through rather than refusing, since Layer 2 (claim-support verification) is the layer designed to catch "relevant-looking but not actually responsive," not Layer 1. First calibration from ~20 queries; revisit with the full Phase 6 eval set.
- 2026-09-12: Layer 2 (claim-support verification) uses a local Ollama model (Qwen 2.5 7B, chosen over the also-available Gemma 2 2B and Llama 3.1 8B for its stronger instruction-following/reasoning at this scale — matters because the whole layer is a precision judgment call) instead of the Claude API the PRD specifies for this layer. Reason: no Anthropic API key is configured for this project yet. Explicit, temporary substitution the user chose after I flagged the blocker, not a silent architecture change — revisit once a key exists. Verified live against 3 real cases: correctly supports a clear TK-non-patentability claim, correctly rejects a claimed specific fee amount against a passage that only says fees are "as prescribed" (the exact case Layer 1's distance threshold alone could not catch — 0.82 distance, under the 0.90 gate), and correctly rejects a claim that actively contradicts a passage about Biological Diversity Act approval requirements. `verify_claim` raises rather than defaults to a verdict on any malformed/incomplete model response, since a verification layer that fails open on a parse error defeats its own purpose.
- 2026-09-12: Layer 2 upgraded to majority-vote verification (3 calls, take the consensus), after directly observing the local 7B model give inconsistent verdicts on the SAME (claim, passage) pair across repeated calls — 2-of-3 correctly supported a genuinely well-supported claim (the PIB patent-count statistic), 1-of-3 incorrectly rejected it (failed to resolve "these" back to its antecedent in the prior sentence). A single unlucky call would have silently produced a false refusal on a correct answer. Also reordered the verification JSON schema to put "reasoning" before "supported" (reason-then-decide, not decide-then-rationalize) — this alone roughly halved the error rate on the same test case before majority voting was added on top. Both changes are direct responses to observed evidence, not speculative hardening.
- 2026-09-12: End-to-end pipeline (`src/generate.py`) initially had a real bug caught by testing on the exact PIB-statistic query used throughout Phase 2-4: authority ordering was applied to the WHOLE candidate pool before truncating to top_k, so several lower-relevance, higher-authority-tier chunks (AYUSH-2025 boilerplate) pushed the actually-relevant chunk (the PIB press release's specific statistic) out of the top_k entirely, causing a false refusal on a query the system had already proven it could answer well in Phase 2/3. Fixed: truncate to top_k by relevance (hybrid rank) FIRST, then apply authority ordering only within that already-selected set — authority is a citation-priority/presentation preference among sources already established as relevant, not a relevance signal itself. Covered by `tests/test_generate.py`.
- 2026-09-12: Generation prompt instructs the model to return an empty claim list rather than state ungrounded specifics, and this worked in practice without Layer 2 needing to intervene: asked for the current patent filing fee (corpus only says fees are "as prescribed," no figures), generation correctly returned zero claims rather than fabricating a number. Layer 2's rejection of a fabricated fee claim was separately verified by constructing that claim directly (see the entry above) — both safety nets are real, not just one covering for an assumption about the other.
- 2026-09-12: `generate.py` switched from raw chunk_id strings to numbered passage labels ([1], [2], ...) for generation to cite, after directly observing the model paraphrase/truncate a chunk_id (e.g. return "ipo_ayush_examination_guidelines_2025" instead of "ipo_ayush_examination_guidelines_2025::preamble") when asked to copy it — the exact-string lookup then silently failed and dropped an otherwise-correct, well-grounded claim, producing a false refusal on a question already validated as answerable in Phase 2. A bare integer is far less prone to that kind of copy error. Found via Phase 6 eval testing, not assumed.
- 2026-09-12: `generate.py`'s CANDIDATE_K raised 20->40 after finding a genuinely correct source chunk (`patents_act_1970::sec-3-clause-d`) ranked #29 by vector similarity for its matching query — outside the previous fetch window entirely, so it was never even considered a candidate regardless of downstream logic. Same statutory-vocabulary-gap pattern documented for §3(p) in Phase 2 (a terse clause vs. a natural-language question), now confirmed recurring on a second, unrelated query — treated as a real, generalizable pattern rather than a one-off. This change is cheap (pure retrieval, no extra LLM calls).
- 2026-09-12: The CANDIDATE_K widening above caused a real regression on re-test (false-refusal rate rose from 5/11 to 7/11) — investigated rather than reverted blindly. Root cause: the generation prompt's "prefer the more authoritative source when they cover the same point" instruction was being over-applied — with more candidates in view, the model started picking a generic, higher-authority-tier passage over a more specific, lower-tier one that actually answered the question, because it satisfied "prefer authority" without checking "do they actually cover the same point" first. Fixed by rewriting the instruction to require finding the most specific/on-point passage FIRST, using authority order only as a tie-breaker among equally-specific candidates. This is a good example of why re-testing after a fix matters — the first fix looked complete until measured again.
- 2026-09-12: `run_phase6.py`'s eval ground truth corrected from one expected doc_id per question to a set of acceptable doc_ids, after discovering during investigation that a citation I'd scored as "wrong" was actually correct: `patents_act_1970::sec-10-sub-4` states the exact same biological-material-disclosure rule as the "expected" TK Guidelines chunk, directly from the Act itself (clause (ii)(D)) — I'd only read the first 600 characters of that passage back in Phase 1/2 and missed it. The single-expected-doc_id scoring was systematically undercounting correct answers whenever the system found a different, equally valid source. Every affected question's corrected ground truth was re-verified against actual chunk text, not guessed or loosened arbitrarily.
- 2026-09-12: Final Phase 6 false-refusal rate (5/11) traced to a genuine local-7B-model extraction-quality limitation, not a further pipeline bug — for the WIPO-toolkit "three phases" question, the exact right sentence was present in the #1-ranked candidate chunk, but generation extracted an unrelated illustrative example from later in that same long, multi-topic chunk instead. Accepted as a documented cost of the temporary local-LLM substitution (see the Layer 2 Qwen 2.5 7B entry above) rather than chased with further prompt engineering, given diminishing returns after 4 confirmed pipeline bugs already found and fixed via this same eval. A stronger model (i.e. the Claude API the PRD specifies) would very likely resolve it.
- 2026-09-12: Observed genuine run-to-run non-determinism in the full pipeline — identical code and questions produced different individual pass/fail patterns across repeated runs (aggregate false-refusal rate was stable at 5/11 across 3 of 4 runs, but which specific questions failed varied). Consistent with the Layer 2 majority-vote finding; a single eval run's numbers should be read as indicative of typical behavior, not an exact, reproducible score.
- 2026-09-13: Replaced the Streamlit UI with FastAPI + a hand-written HTML/CSS/JS front end in `web/`. Streamlit re-renders the whole page per interaction and gives no control over transitions, so it can't show the pipeline working live — and the pipeline working live is the product's whole differentiator, not decoration. The PRD (§7) already allows either. No build step or framework, so there's nothing between the source and a demo screen that can break.
- 2026-09-13: The UI is a chat application, not a search page. First version was a single-shot query form; rebuilt after user feedback pointed out the real usage pattern — an IP officer asks, reads, asks a follow-up, copies a citation into a file note, and comes back the next day wanting the thread. That dictates: sidebar of past consultations (localStorage), a scrolling thread, and a composer pinned to the bottom so results never render somewhere the user has to hunt for.
- 2026-09-13: `generate.answer_query_streaming` added as a generator yielding one event per pipeline stage, with `answer_query` reduced to a thin wrapper that drains it — no logic duplicated, and every existing test and gate script keeps working untouched. `/api/ask` forwards those events as SSE so the UI can show each layer's decision as it happens; a local model takes 20-40s, and that time is more honestly spent showing the verification than hiding it behind a spinner.
- 2026-09-13: The verification stepper collapses to a one-line badge once it settles, rather than staying expanded. Expanded-forever would make a daily-use thread unreadable after a few questions; collapsed-by-default would bury the one thing that distinguishes this system. Collapsing on completion (re-expandable) gets both.
- 2026-09-13: Follow-up questions are resolved by rewriting them into a standalone question (`generate._condense_followup`, one extra local-LLM call using the last 3 turns) BEFORE retrieval, rather than feeding conversation history into generation/verification directly. This keeps the grounding guarantee intact: a bad rewrite can only mis-target retrieval, which Layer 1/2 still catch (verified live — a genuinely ambiguous test follow-up produced a plausible-but-wrong rewrite, and the pipeline correctly refused rather than fabricating an answer). Feeding history straight into generation would let it assert something from the conversation instead of the corpus, defeating the whole point of Layer 2.
- 2026-09-13: `GENERATION_MODEL` (generate.py) and `MODEL` (verification.py) now both read `OLLAMA_MODEL` from the environment (default `qwen2.5:7b`) instead of being hardcoded in two places, and a new `/api/config` endpoint exposes the value so the UI's model badge always names whatever is actually configured — swapping models means setting one env var, not editing code and the UI to match.
- 2026-09-13: Decided against a table/column renderer for comparison-style questions. Every claim in this pipeline is verified against exactly one source passage (Layer 2's whole mechanism); a table cell comparing two things would need either fabricated structure the model was never asked to justify, or a second verification scheme for cells, which is a materially bigger change than this session's scope. The existing claim list — each claim citation-tagged with its source's authority tier — already lets a reader compare sources; flagged as a possible dedicated phase later rather than bolted on now.
- 2026-09-13: Second corpus-sourcing pass, at the user's request ("get as many documents and sources as possible"). Added two: the Biological Diversity Act, 2002 (closes a real gap found live during UI testing — its §55 penalty provision had only ever been indexed secondhand via the 2012 IPO guideline's summary) and the WIPO Treaty on IP, Genetic Resources and Associated Traditional Knowledge, 2024 (covers the "international regimes" half of the PRD's own problem statement, previously unrepresented). Rejected a third candidate — the Patents Rules, 2003 / Patents (Amendment) Rules, 2024 pair, which would also have given a genuine two-version authority-conflict test case — because the only available mirror of the base 2003 rules was a corrupted OCR scan (confirmed word-level corruption: "Govemment", "MINlSTRY", digit/letter confusion). The PRD's own Data Plan says a smaller clean corpus beats a large noisy one; that call was made literally, not just quoted. See `corpus/manifest.md` for the full sourcing trail including dead links tried.
- 2026-09-13: Extended `chunking.py` with a second structural-numbering pattern — treaty-style "ARTICLE N" with the title on the following line — activated only as a fallback tried after the existing numeric "N. Title.—" pattern finds fewer than 2 matches (see `_chunk_region`), so it's additive and can't change how any of the previously-verified 5 documents chunk. Reuses the existing oversized-section and lettered-clause splitting helpers rather than duplicating them. Chose this over a text-preprocessing hack (rewriting "ARTICLE N" into the numeric form before chunking) because that would have meant the stored chunk text no longer matched what the source document actually says — unacceptable for a citation-verification tool.
- 2026-09-13: `authority.py`'s new WIPO GRATK Treaty entry is deliberately tagged `Informational`, not `Act`, even though it's a real, adopted treaty text — because it is not yet in force (needs 15 ratifications/accessions, not yet reached as of sourcing). Its `short_name` says "not yet in force" directly in the string that gets shown in every citation built from it, so a generated answer can't accidentally present it as binding Indian law without that caveat riding along. Layer 3's authority ranking also means it will never be preferred over an actual Act or Guideline addressing the same point.
- 2026-09-13: The sidebar's "N primary sources indexed" line was hardcoded to "5" in `index.html`, gone stale the moment the corpus grew to 7 today. Fixed the same way as the model badge: `/api/config` now also returns `corpus_docs` (`len(authority.DOC_AUTHORITY)`), and the UI reads it — one source of truth, so the number can't go stale again next time the corpus changes.
- 2026-09-13: Live-verified the new corpus content post-rebuild and found a real, reproducible generation-quality issue: asking about the GRATK Treaty's Article 3 disclosure requirement — across 4 differently-worded attempts, including one naming "Article 3" directly — the local model kept drafting a claim describing "the Toolkit" (the pre-existing, separate WIPO TK documentation toolkit) even though the treaty's own Article 3 text was correctly retrieved and given to it every time (confirmed directly via `_select_grounded_hits_with_diagnostics`). Two WIPO-published documents both discussing documenting/disclosing genetic-resources-related TK appears to be a harder discrimination case for a 7B model than the corpus's other same-tier pairs. Added a source short_name label to each numbered passage in `_build_passages_block` as a partial mitigation (didn't fully fix it in testing, but is a strict improvement and harmless elsewhere). Critically, **Layer 2 correctly rejected every one of these mismatched claims** — the user never received a false answer, only a refusal — which is the system's core safety property holding under a new, harder case, not a new failure mode. Documented as an added-scope instance of the pre-existing local-model extraction-quality limitation (see Phase 6 findings), not a new class of bug. Not chased further today (would mean deeper prompt engineering against a model this project already plans to replace once an Anthropic API key exists).
- 2026-09-13: User has a real Anthropic API key but wants it held back until deployment, to avoid burning through its rate limits during development — reasonable, and not something to work around by using it anyway. Asked instead to keep the architecture "upgradable" so the swap is trivial when the time comes.
